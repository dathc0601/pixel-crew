# Performance baseline and Phase 4 results (2026-11-07)

Before = `master` at the start of Phase 4 (`851dfc5`). After = branch `phase-4-performance`.
Both were measured the same way, on the same machine (macOS arm64, Node 22.19), with
production builds: the static web export served by the gateway bundle
(`node apps/gateway/dist/index.js --demo`) and a temporary `PIXEL_CREW_HOME`. Demo mode
only: scripted fake agents, no AI CLI, no tokens.

## Summary

| Metric | Before | After |
|---|---|---|
| Idle (nobody works): renders / ticks per 3 s | 0 / 0 | 0 / 0 |
| Typing (4 devs working, nobody walks): renders / ticks per 3 s | 22 / 44 | 22 / 22 |
| Walking (hand-off walks): renders / ticks per 3 s | 180 / 180 (60 Hz display) | 90 / 90 (30 fps cap; 120 Hz display) |
| Hidden tab or off-screen canvas | rAF stops (browser), wake-up timers keep firing | loop paused: 0 ticks, 0 timers |
| Frame render time, cached static layer vs full redraw (same build, 60 redraws × 3) | 1.46–1.65 ms | 0.60–1.04 ms |
| `/office` first-load JS (Next "First Load JS") | 242 kB | 158 kB |
| `/office` first-load JS including the root layout's chunks | not measured | 184 kB |
| `apps/web/out` | 2.5 MB | 2.7 MB (+160 KB self-hosted fonts) |
| Daemon RSS, demo, 6 / 3 / 0 agents idle (60 s) | 79.8 / 80.7 / 81.1 MB | 77.6 / 78.5 / 79.1 MB |
| Daemon CPU, same runs | 0.02 / 0.02 / 0.02 % | 0.02 / 0.02 / 0.03 % |

"Ticks" are update passes of the game loop (`window.__pixelCrewLoop.ticks`); "renders" are
frames drawn (`.renders`). The new loop also counts `rafCallbacks` (vsyncs skipped by the
30 fps cap cost about 0.2 ms each) and `renderMs`.

## How it was measured

- **Browser** (Playwright, Chromium, 1440×900, DPR 1, office view):
  - idle: 3 s with nobody working;
  - typing: `RUN_TASK` straight to the four devs (no hand-off walk), sampled 3 s after;
  - walking: Boss → Lead hand-off right after "Hand it to the Lead", then the Lead's walks to the devs.
  The headless display ran at 60 Hz in the before session and 120 Hz in the after one; the
  after numbers are capped at 30 fps either way (before would have been 360 ticks at 120 Hz).
- **Frame time:** `window.__pixelCrewDebug.staticCache = false` (full redraw) vs `true`, 60
  forced redraws each, three rounds, average `renderMs` per frame.
- **Bundle:** `next build` output, and source-map-explorer on a build with
  `PIXEL_CREW_SOURCE_MAPS=1`. `pnpm --filter web size` prints the gated numbers.
- **Daemon:** `ps -o time=,rss=` before and after 60 s with no client connected, after firing
  agents down to 3 and 0 over the WebSocket API.

## `/office` first-load chunks (gzip)

Before (242 kB):

| Chunk | gzip | Main contents |
|---|---|---|
| framework (`4d67e943`, `3388`, webpack, main-app) | 105 kB | Next.js / React runtime, workbox-window |
| `8606` | 64.0 kB | **zod** (55 kB raw), **react-markdown + remark-gfm + micromark** (~100 kB raw), Radix dialog + react-remove-scroll |
| `app/office/page` | 57.2 kB | the office page, office-store, sprites, editor actions, `packages/shared` schemas |
| `9053` | 12.2 kB | tailwind-merge, Radix primitives |

After (158 kB): framework 106 kB + `app/office/page` 52.3 kB. The root layout adds 26 kB
(`5050`, `3174`, `9342`: tooltip provider, tailwind-merge, Radix) that Next's column does not count.

What moved out of first load:

- Markdown: `SysMsg`/`TokenBadge` and the confirm dialog are `next/dynamic` now, so react-markdown, remark-gfm and the Radix dialog load with the first chat line or confirm.
- Zod: the web client imports `@pixel-crew/shared/client` (constants, presets, types, `parseGatewayEventLite`); a lint rule blocks runtime imports of the Zod entry in `apps/web`.
- Already lazy before Phase 4 and confirmed absent from first load: Ably, JSZip, the layout editor toolbar, the other dialogs and panes.

Not done (would take `/office` further down): the office page chunk still carries the sprite data, the asset loader and the editor actions used by `useEditorActions` (about 20 kB gzip together), and the root layout's tooltip provider. Below 170 kB was reached, so a Vite/Preact move (§7.1) is not needed.

## Static layer parity

Cached frames were compared with full redraws of the same state, pixel by pixel
(`getImageData`), in the built app: 0 differing pixels at DPR 1 (with a hover outline), 2
and 3. At fractional DPRs (e.g. 2.625 phones) tile and sprite edges fall between device
pixels and a partial redraw cannot reproduce those anti-aliased seams exactly, so the
renderer draws in full there. The layout editor also draws in full.

## Daemon notes

Demo mode never ran the external-agent scanner, so the demo numbers above barely move. The
Phase 4 changes cut work that demo mode does not show: outside demo mode the scanner ran
`ps` every 7 s from startup, with or without a browser. Now it runs only while a viewer is
connected and can be turned off (`"externalAgents": false`). Agent CLIs were not started
for this measurement (the plan's 0/3/8 became 0/3/6, the demo team size).
